Ты прошёл Node.js изнутри: Event Loop, стримы, модули CJS/ESM. Теперь самое время ответить на вопрос, который отделяет «пишу скрипты на Node» от «строю backend-приложение»: как организовать код так, чтобы он не рассыпался через полгода и чтобы новый разработчик сел в проект за день, а не за месяц.

Этот раздел — про три вещи сразу. Первая — **архитектура приложения** на примере NestJS: модули, провайдеры, контейнер внедрения зависимостей. Вторая — **жизненный цикл запроса**: как запрос проходит через middleware, [guards](https://docs.nestjs.com/guards), pipes, interceptors и filters, и почему этот порядок — контракт, а не произвол. Третья — **дизайн API как контракта**: REST в деталях, [OpenAPI](https://spec.openapis.org/oas/v3.1.0)-документация, [GraphQL](https://graphql.org/learn/) и [gRPC](https://grpc.io/docs/what-is-grpc/core-concepts/) — три подхода к одной задаче «отдать данные клиенту» с разными компромиссами.

## Зачем именно NestJS

Express — это фантастический HTTP-движок и ужасный каркас приложения. Он не говорит тебе, где лежит бизнес-логика, как разделить проект на части и как сделать так, чтобы двадцать сервисов не превратились в двадцать уникальных способов делать одно и то же. NestJS берёт проверенную серверную практику — модули, DI, декораторы, единый пайплайн запроса — и переносит её в мир TypeScript (см. [официальную документацию](https://docs.nestjs.com/first-steps)). Под капотом тот же Express (или Fastify), вся магия из урока про Event Loop работает без изменений, но сверху появляется архитектура.

:::tip[Pet-проект]
Весь раздел закрепляй на pet-проекте: это API твоего приложения — задачник, магазин или блог. К концу раздела у тебя должен быть спроектированный REST API с OpenAPI-документацией, защищённый guards и валидируемый pipes, с одним GraphQL-экспериментом и одним gRPC-вызовом между двумя сервисами.
:::

## Порядок глав

1. **[NestJS: модули, провайдеры, DI](/07-nestjs-api/nestjs-foundation/)** — фундамент фреймворка. Разбираем, как устроен DI-контейнер: рефлексия метаданных, декораторы, `emitDecoratorMetadata`. Учимся регистрировать провайдеры через `useClass` / `useFactory` / `useValue`, управлять scope'ами (DEFAULT / REQUEST / TRANSIENT) и разруливать циклические зависимости через `forwardRef`. Это глава, без которой остальные не имеют смысла.
2. **[Жизненный цикл запроса](/07-nestjs-api/nestjs-request-lifecycle/)** — middleware → guards → interceptors → pipes → handler → interceptors → filters. Строим ролевую модель на metadata и `Reflector`, валидируем DTO через `class-validator`, пишем interceptor для логирования и единый exception filter. Поймёшь, почему порядок этапов — это не эстетика, а производительность и безопасность.
3. **[REST-дизайн и OpenAPI](/07-nestjs-api/rest-design/)** — ресурсное моделирование, вложенные ресурсы, идемпотентность методов, разбор статус-кодов, версионирование, пагинация offset vs cursor, фильтрация и сортировка, идемпотентные ключи. Заканчиваем автогенерацией OpenAPI-схемы из декораторов и красивой документацией на Scalar.
4. **[GraphQL, DataLoader, gRPC](/07-nestjs-api/graphql-grpc/)** — два альтернативных протокола. GraphQL: схема, резолверы, подписки, проклятие N+1 и его лечение через DataLoader. gRPC: Protocol Buffers, четыре вида RPC, генерация кода, транспорт микросервисов в NestJS. В конце — честное сравнение REST / GraphQL / gRPC и критерии выбора.

## Как этот раздел связан с остальным учебником

NestJS стоит на плечах Node.js из [прошлого раздела](/06-nodejs/event-loop-node/): каждый guard, pipe и interceptor — обычная асинхронная функция в том самом Event Loop. Дальше раздел опирается на [PostgreSQL и Redis](/08-data/): сервисы, которые ты пишешь здесь, будут доставать данные из БД, а guards — проверять JWT, которые разберём в [главе про аутентификацию](/09-security-testing/auth-jwt-oauth/). Наконец, спроектированный здесь API ты потом упакуешь в Docker-образ и выкатишь через CI/CD — [этапы 10–11](/10-linux-docker/docker-deep/).

:::note[Критерий готовности]
Раздел пройден, когда ты можешь: объяснить, как NestJS узнаёт типы для DI без явной регистрации; нарисовать пайплайн запроса и обосновать порядок этапов; спроектировать REST API с cursor-пагинацией и задокументировать его через OpenAPI; сказать, когда вместо REST нужен GraphQL, а когда — gRPC.
