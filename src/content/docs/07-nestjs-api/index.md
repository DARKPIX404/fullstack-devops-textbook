Ты прошёл Node.js изнутри: Event Loop, стримы, модули CJS/ESM. Теперь самое время ответить на вопрос, который отделяет «пишу скрипты на Node» от «строю backend-приложение»: как организовать код так, чтобы он не рассыпался через полгода и чтобы новый разработчик сел в проект за день, а не за месяц.

Этот раздел — про четыре вещи сразу. Первая — **архитектура приложения** на примере NestJS: модули, провайдеры, контейнер внедрения зависимостей. Вторая — **жизненный цикл запроса**: как запрос проходит через middleware, [guards](https://docs.nestjs.com/guards), pipes, interceptors и filters, и почему этот порядок — контракт, а не произвол. Третья — **дизайн API как контракта**: REST в деталях, [OpenAPI](https://spec.openapis.org/oas/v3.1.0)-документация, realtime-протоколы ([WebSocket](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API) и SSE), [GraphQL](https://graphql.org/learn/) и [gRPC](https://grpc.io/docs/what-is-grpc/core-concepts/) — подходы к задаче «отдать данные клиенту» с разными компромиссами. Четвёртая — **асинхронность между сервисами**: очереди сообщений и outbox-паттерн для работы, которая происходит после ответа клиенту.

## Зачем именно NestJS

Express — это фантастический HTTP-движок и ужасный каркас приложения. Он не говорит тебе, где лежит бизнес-логика, как разделить проект на части и как сделать так, чтобы двадцать сервисов не превратились в двадцать уникальных способов делать одно и то же. NestJS берёт проверенную серверную практику — модули, DI, декораторы, единый пайплайн запроса — и переносит её в мир TypeScript (см. [официальную документацию](https://docs.nestjs.com/first-steps)). Под капотом тот же Express (или Fastify), вся магия из урока про Event Loop работает без изменений, но сверху появляется архитектура.

:::tip[Pet-проект]
Весь раздел закрепляй на pet-проекте: это API твоего приложения — задачник, магазин или блог. К концу раздела у тебя должен быть спроектированный REST API с OpenAPI-документацией, защищённый guards и валидируемый pipes, с real-time уведомлениями через WebSocket или SSE, одним GraphQL-экспериментом, одним gRPC-вызовом между двумя сервисами и фоновой задачей на очереди с outbox-паттерном.
:::

## Порядок глав

1. **[NestJS: модули, провайдеры, DI](/07-nestjs-api/nestjs-foundation/)** — фундамент фреймворка. Разбираем, как устроен DI-контейнер: рефлексия метаданных, декораторы, `emitDecoratorMetadata`. Учимся регистрировать провайдеры через `useClass` / `useFactory` / `useValue`, управлять scope'ами (DEFAULT / REQUEST / TRANSIENT) и разруливать циклические зависимости через `forwardRef`. Это глава, без которой остальные не имеют смысла.
2. **[Жизненный цикл запроса](/07-nestjs-api/nestjs-request-lifecycle/)** — middleware → guards → interceptors → pipes → handler → interceptors → filters. Строим ролевую модель на metadata и `Reflector`, валидируем DTO через `class-validator`, пишем interceptor для логирования и единый exception filter. Поймёшь, почему порядок этапов — это не эстетика, а производительность и безопасность.
3. **[REST-дизайн и OpenAPI](/07-nestjs-api/rest-design/)** — ресурсное моделирование, вложенные ресурсы, идемпотентность методов, разбор статус-кодов, версионирование, пагинация offset vs cursor, фильтрация и сортировка, идемпотентные ключи. Заканчиваем автогенерацией OpenAPI-схемы из декораторов и красивой документацией на Scalar.
4. **[Realtime API: WebSocket и SSE](/07-nestjs-api/async-realtime/)** — чем realtime отличается от request/response: WebSocket handshake и фреймы под капотом, NestJS Gateway с комнатами, авторизация JWT в handshake, SSE для односторонних событий, reconnect с backoff, backpressure и heartbeat, масштабирование через Redis Pub/Sub adapter и проксирование через Nginx.
5. **[GraphQL, DataLoader, gRPC](/07-nestjs-api/graphql-grpc/)** — два альтернативных протокола. GraphQL: схема, резолверы, подписки, проклятие N+1 и его лечение через DataLoader. gRPC: Protocol Buffers, четыре вида RPC, генерация кода, транспорт микросервисов в NestJS. В конце — честное сравнение REST / GraphQL / gRPC и критерии выбора.
6. **[Очереди и outbox на практике](/07-nestjs-api/messaging-outbox/)** — асинхронность между сервисами: проблема двойной записи, outbox pattern в PostgreSQL, RabbitMQ (exchange, binding, routing key), retry через TTL/DLX, DLQ, идемпотентный consumer, упорядоченность и честное сравнение брокеров.

## Как этот раздел связан с остальным учебником

NestJS стоит на плечах Node.js из [прошлого раздела](/06-nodejs/event-loop-node/): каждый guard, pipe и interceptor — обычная асинхронная функция в том самом Event Loop. Realtime и очереди опираются на [Redis](/08-data/redis-structures/) (Pub/Sub adapter, Streams) и [PostgreSQL](/08-data/postgres-transactions/) (outbox-таблица в той же транзакции, что и бизнес-данные). Дальше раздел опирается на [PostgreSQL и Redis](/08-data/): сервисы, которые ты пишешь здесь, будут доставать данные из БД, а guards — проверять JWT, которые разберём в [главе про аутентификацию](/09-security-testing/auth-jwt-oauth/). Наконец, спроектированный здесь API ты потом упакуешь в Docker-образ и выкатишь через CI/CD — [этапы 10–11](/10-linux-docker/docker-deep/).
